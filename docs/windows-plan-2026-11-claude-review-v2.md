## 新規・残存指摘（重大度順）

### 高

**F01 段階ゲートのRelease検証が、版照合のため実行できない**
- **対象**: 計画114-115行（段階ゲートでのDebug/Release検証）、125-128行、N05/N15/N16
- **根拠**:
  - `build-release.ps1`は、`version.txt`の数値部分が`build.zig.zon`と違うと必ず止まります（`scripts/build-release.ps1:76`→`scripts/windows-version.ps1:50-51`）。`-Dversion-string`の指定も拒否します（`build-release.ps1:70-73`）。
  - 現在のgoozttyは`version.txt`が`1.3.2-windows.17`、`build.zig.zon`が`1.3.2-dev`です。Cは`1.4.1-dev`、Bはv1.4.0なので、おそらく`1.4.0`です（未確認）。Aでの値も未確認です。
  - このため、windowsではB・Cの段階で照合に失敗するのが確実です。windowsの`version.txt`の値（handoffでは「cutover時の値」）は未確認ですが、数値部分は1.3.2のはずです。
  - goozttyでも、B段階では`1.4.0-windows.N`が必要になります。しかし計画は`1.4.1-windows.N`の最終値しか定めていません（125行）。
  - 127-128行は「障害になる場合は…検討する」と書いていますが、障害は起きるものと見るべきです。しかも誰がいつ決めるかがありません。
- **影響**: 11/16〜20のP2/P3ゲートがRelease手順の段階で止まります。中間版の値を場当たりで決めるか、ゲートを黙って省略することになり、「黙ってチェックを無効にしない」という128行の方針とも衝突します。
- **修正案**: N03の完了条件に、段階ごとの版の扱いを決めることを加えてください。選択肢は次の3つで、私の推奨は(a)です。
  - (a) 段階ゲートのRelease相当検証は、`build-release.ps1`と同じ引数で`zig build -Doptimize=ReleaseFast -Dcpu=baseline`を直接実行する。`build-release.ps1`は最終版を設定したN17以降だけで使う。
  - (b) windows側の検証専用の手段を、所有者の承認を得てN05の範囲で追加する。
  - (c) goozttyで各段階の`X.Y.Z-windows.N`を正式に採番する。
  - A時点の`build.zig.zon`の値も、N03で確認する事項に加えてください。

### 中

**F02 段階が不合格のときの戻し方と、候補SHAの扱いが未定義**
- **対象**: 第8節166-167行と171行、第3節64行
- **根拠**:
  - AGENTS.md 33-36行の方針は「所有ブランチへ直接コミットし、PRは使わない」です。
  - Bを`windows`/`gooztty`へコミットした後にゲートが不合格になると、両ブランチはB込みの状態になります。そこから「直前に合格したA」を候補にする方法がありません。
- **影響**: 11/20の分岐でAを候補に選んでも、その実体（どのSHAか、以後の修正をどこに積むか）が決まりません。
- **修正案**:

  - 段階の統合は作業用ローカルブランチで検証し、合格後に本ブランチへ反映すること、またはそれに代わる手順を明記してください。
  - 各段階のコミットには所有者の指示が必要です（136行）。日程が所有者の都合に左右されることも書き添えてください。

**F03 凍結候補の同一性の定義が不足している（N17/N06/N11/N18）**
- **対象**: N17（85行）、107・109行、121行、126行、149行
- **根拠**:
  - `verify-windows-ime.ps1`と`verify-windows-lifecycle.ps1`は、作業ツリーから独自にDebugビルドを作って試験します（`verify-windows-ime.ps1:61-62`、`verify-windows-lifecycle.ps1:68-69`）。N17で固定するRelease exeのhashとは必ず一致しません。
  - `version.txt`の`N`は「着手時に決める」（126行）とされています。版はexeに埋め込まれるので、N17より後に`N`を決めるとexeが新しい候補になり、121行の規則によりN11を再試験しなければなりません。
  - 署名すると実行ファイルのhashも変わります。
- **影響**: N06/N11/N18が同じ候補を試したことを示せません。
- **修正案**: N17で次の3つを固定してください。
  - gooztty上のコミットSHAとクリーンな作業ツリー
  - 確定した`version.txt`（`N`を含む）
  - 通常版とhook版のRelease exeのhash

  あわせて次の点を明記してください。
  - 自己ビルドするスクリプトの結果は、同じSHAかつ作業ツリーに変更がない状態（`summary.json`の`Commit`/`WorkingTree`）で照合する。
  - N18は同じSHAと同じ版から作られた署名成果物であることを確認し、署名前のhashまたはビルド記録と照合する。

  現在の作業ツリーにある未追跡のレビュー文書も、`WorkingTree`に記録されます。
