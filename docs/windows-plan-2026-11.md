### 段階の保存と不合格時の扱い

N05/N15/N16では、統合前と合格後のmain/windows/goozttyのSHA、取り込んだ上流SHA、
ソース状態、検証コマンド・ビルド条件・成果物hash・結果の保存先を段階台帳に記録する。
コミットは所有ブランチへ直接行う規則を維持し、作業用ブランチへのコミットを前提にしない。
コミットは所有者の明示指示がある場合のみ行う。合格内容を固定したコミットがまだない場合は、
パッチとファイルhashを保存して未確定とし、次の段階へ進めない。所有者の指示待ちも日程へ計上する。

不合格の作業・ログは保存し、`reset --hard`、無断のrevert、既存作業ツリーの破棄で戻さない。
直前合格の候補を再検証する場合は、台帳に記録したwindows/goozttyのコミットから、
リポジトリ内の検証用ディレクトリにdetached worktreeを作成する手順とする。
そこで履歴やソースを変更せず、その合格版を再現する。旧SHAに修正コミットを積まない。
旧候補へ追加修正が必要なら代替候補の受入を止め、所有ブランチでの前進修正または別の履歴操作を
所有者と決定して計画を改訂する。最終版の採番変更が必要な旧候補も、この制約に含む。
使用するSHAを記録できない、または合格版を再現できない場合は候補なしとして受入を延期する。

### 中間段階の最適化ビルド

N04とP1〜P3ではwindows/goozttyとも配布用`build-release.ps1`を使わず、`zig build`を直接実行する。
Zig 0.16のN04では`-Doptimize=ReleaseFast`、Zig 0.17のA/B/Cでは`-Doptimize=fast`を使う。
N03で固定ソースのビルド定義と各Zig版の`zig build --help`により引数を確認済み。Windowsアプリの移行後の実行結果はN05以降で記録する。
既存共有キャッシュではhash不一致が出たため、[事前確認記録](windows-november-preflight.md)のように検証キャッシュを分離する。
通常版の実行形は次のとおり（`<段階専用prefix>`はA/B/C・ブランチ・試行ごとの未使用ディレクトリに置き換える）。

```powershell
# N04: Zig 0.16.0
zig build --prefix <段階専用prefix> -Doptimize=ReleaseFast -Dcpu=baseline -Demit-docs=false --summary all
# P1〜P3: Zig 0.17.0、移行後の引数確認を経て実行
zig build --prefix <段階専用prefix> -Doptimize=fast -Dcpu=baseline -Demit-docs=false --summary all
```

hook版は同じコマンドに`-Dwin32-test-hooks=true`を加え、別prefixを使う。
`-Dversion-string`による上書きやversion.txtの書き換えは行わず、ソース由来の版を記録する。
事前に`scripts/fetch-conpty.ps1`で固定依存を準備し、ConPTY同梱ファイルの配置・版・hashと
実際に使用したバックエンドを確認する。prefixは使い回さず旧成果物の混入を避ける。
直接ビルドには配布スクリプトの検査がないため、起動、CLI/ファイルの版、icon/manifest、
ブランド・リソース・terminfoの存在と参照先を個別に確認し記録する。配布物として扱わない。

P1〜P3の段階ゲートは、windowsでDebug/上記最適化ビルド・全Zigテスト・通常/hook Win32テスト、通常GUI/IOと各段階の重点検証を実施する。
その後goozttyへ統合し、全Zigテスト・Debug/最適化ビルド・通常GUI/IOと重点項目を再検証する。
Aでは両ブランチでGPU/復帰の制御試験と`verify-windows-ime.ps1`を必須とする。
Bの初期化解放変更ではlifecycle、Cの設定変更では設定診断も両ブランチで実施する。
N15でlifecycleのケース数・画像数が変わる場合は、旧新の対応、追加/削除理由と期待結果を記録する。通過のために件数だけを変更しない。
段階で実施した全マトリクスの記録をN06で再利用できるのは、ソース・ビルド・試験条件が最終候補と同一の場合だけ。

再実行で成功しても最初の失敗を消さず、再現条件、試行回数、各終了コードを残す。
N17でコードを凍結し、N06/N11中に実GPU障害試験や同一環境を操作する別GUI試験を並行させない。
凍結後の修正は新しい候補としてhashを付け直し、影響する受入を再実行し、N11は新候補で180分を完走する。
凍結後にソース・版・依存・ビルド条件を変更した場合、11月の余裕枠で完了を約束せず、N11を12月以降へ延期する。

## 6. 版番号・ブランチ差分・配布受入

Cの数値ベースは1.4.1。goozttyのversion.txtを`1.4.1-windows.N`形式で整合させる。
NはN17の凍結前にタグ・リリース・[版更新チェックリスト](version-update-checklist.md)を確認して確定する。
windowsのversion.txtは変更しない。現時点では`1.3.2-windows.16`で、B/Cのベースとは一致しないため、
中間検証には第5節の直接ビルドを使う。goozttyの中間検証も同じ方式で行う。
ブランチ規則に従い、各マージでversion.txtの数値ベースを上流に整合させる。
Bでは`1.4.0-windows.1`へ整合済みだが、これは開発段階の値であり、配布候補の確定ではない。
changelog/release notesも開発段階の記録として区別し、最終配布候補の採番はN17で改めて確定する。
最終goozttyの版確定・コミット後にのみ`build-release.ps1`を使い、その版照合は維持する。
N05でスクリプトのZig 0.17構文対応を行い、N17で通常/hookの専用出力を作成してスクリプトの検査も完了させる。

### 最終候補の同一性

N17では、所有者がコミットを指示した固定gooztty SHAからクリーンな検証用worktreeを用意する。
版変更が未コミット、または必要なコミット指示が未取得なら凍結完了とはしない。
レビュー文書を含む未コミットの既存作業を消去・無断コミットせず、既存チェックアウトとは分離する。
候補台帳にはSHA、version.txt全値、Zig版、依存の固定値/hash、CPU/最適化/引数、
生成prefix、通常/hook Release exe hash、付随リソースhashとビルドログを保存する。

自己ビルドするIME/lifecycle検証は別のDebug/hookバイナリなので、Releaseとexe hashが異なってよい。
同じ固定SHA・版・依存からのビルドであること、実行前後のtracked差分と未追跡ソースがないこと、
各variantの引数・exe hashを照合する。ビルドが作る無視対象のログ/成果物は別途記録し、ソース変更と区別する。
各スクリプトのsummaryに加え、必要なgit状態と依存hashを補足記録する。
N06の通常Releaseによる実操作とN11は、N17の同一通常Release exeを使う。

N18では同じSHA・版・依存・ビルド条件で所有者が作成した成果物であることをビルド記録で照合する。
署名前/後のexe hashと署名検証結果、インストーラー等のhashを記録する。
署名でhashが変わること自体をソース変更とは扱わない。再ビルドで署名前hashが異なる場合は、
ビルド条件との差を評価し、同一候補と判断できなければ新候補としてN06/N11を再実施する。

2026-10-31時点のコミット間コード差分はsrc/brand.zigだけだが、永久の制約とはしない。
各統合で許容したGooztty独自差分を一覧化し、Windows移植修正の取り残しや逆流がないことを確認する。

11月の技術目標はN05/N15/N16/N17/N06/N11の完了まで。署名配布物の更新・新規インストール・
アンインストール受入はN18として別管理し、所有者が成果物を用意した後に行う。
N18が残る間、#50全体や配布受入完了とは報告しない。
本計画の改訂は実際のmerge・commit・tag・push・パッケージ作成・公開の指示ではない。
