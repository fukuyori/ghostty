# Ghostty Version Update Checklist

This document is a checklist for changing the Ghostty core version in this
fork, so that no update location or verification step is missed. It focuses
mainly on preparing the Windows distribution, but the existing upstream build
rules are kept as well.

## 1. Current Version Paths

| Location | Role | Normal update |
|---|---|---|
| `.version` in `build.zig.zon` | Base version of Ghostty core used for Git checkouts | **Required** |
| Git branch name, commit hash, tag | Pre-release/build metadata for normal builds | Automatic |
| `-Dversion-string=X.Y.Z` | Overrides the base version in CI or explicit verification | Conditional |
| `dist/windows/version.txt` | Windows preview version (`X.Y.Z-windows.N`) read by the release and installer scripts | **Required** for each Windows preview |
| `VERSION` in the source tarball | Version used for distributed sources without Git information | Generated by `zig build dist` |
| `lib_version` in `build.zig` | Independent version of `libghostty-vt` | Only when releasing the library |
| `src/build/WindowsVersionResource.zig` | Generates the Windows resource header at build time | Automatic |
| `dist/windows/ghostty.rc` | Embeds the generated values into the Windows file properties | Normally no change needed |

Do not place `VERSION` in a normal Git checkout. If it exists, it takes
precedence over `build.zig.zon`, so do not create or update it by hand.

For a Windows-preview-only increment, update these files together:

- `dist/windows/version.txt`: the new preview number.
- `docs/windows-changelog.md`: changes assigned to that preview.
- `docs/windows-release-notes.md`: preparation/release status, verification,
  and limitations. Distinguish prior Debug checks from distribution checks.
- `docs/windows-roadmap.md`: working-tree version, published version, and
  remaining release work.

Keep `build.zig.zon` and `lib_version` unchanged when only incrementing the
Windows preview sequence. Historical release entries retain their versions.

The `.version` in `pkg/*/build.zig.zon` is the version of each dependency
component and is not changed when updating the Ghostty core version.

## 2. Before Updating

- [ ] Decide whether the target is Ghostty core, `libghostty-vt`, or both.
- [ ] Confirm that the new value follows the Semantic Versioning format.
- [ ] Check existing work with `git status --short` and do not mix in unrelated
  changes.
- [ ] Confirm that no `VERSION` remains at the repository root.

```powershell
Test-Path -LiteralPath VERSION
git status --short
```

## 3. Updating Ghostty Core

- [ ] Update `.version` in `build.zig.zon`.
- [ ] On development branches, set `.version` to `X.Y.Z-dev`, indicating the
  target release series. When merging upstream, match upstream's `.version`.
- [ ] When verifying an official release equivalent to upstream, write `X.Y.Z`
  to `dist/windows/version.txt` and use `vX.Y.Z` for the tag, without a
  pre-release part.
- [ ] When publishing a Windows preview, write `X.Y.Z-windows.N` to
  `dist/windows/version.txt` and tag it `vX.Y.Z-windows.N` (see "Windows
  Preview Version Numbers" below).

### Windows Preview Version Numbers

The Windows builds published by this fork append the Windows sequence number
to the upstream base version as a pre-release identifier.

| Example | Meaning |
|---|---|
| `1.3.2-windows.1` | First Windows preview based on the upstream 1.3.2 series |
| `1.3.2-windows.2` | Fixed release on the same base version |
| `1.3.3-windows.1` | First preview after merging the upstream 1.3.3 series |

- The base version `X.Y.Z` must match the numeric part of `.version` in
  `build.zig.zon`. Even for a series upstream has not released yet, use the
  version under development (the numeric part of `X.Y.Z-dev`).
- The pre-release identifier `windows.N` sorts before the official `X.Y.Z` in
  SemVer, so the ordering stays intact even if upstream later publishes
  `X.Y.Z`. Do not use build metadata such as `X.Y.Z+windows.N` to distinguish
  the build, because that would claim an unpublished official version.
- The sequence number `N` starts at 1 and restarts for each base version. It is
  compared numerically, so `windows.10` is newer than `windows.9`.
- The sequence number is reflected in the fourth element of the Windows numeric
  version (Section 6). The upper limit is 65535.
- The version of a Windows preview lives in `dist/windows/version.txt`, one
  line holding `X.Y.Z-windows.N` and nothing else. Raising the version means
  editing this file.
- `scripts/build-release.ps1` reads the file from the working tree and passes
  it as `-Dversion-string`. The result does not depend on Git: the same version
  is built whether the changes are committed or not and whether `HEAD` carries
  the tag or not.
- The scripts do not take a version. A version given on the command line would
  only put another number on the current sources, not build that version, so
  `build-release.ps1` rejects `-Dversion-string` in `-AdditionalZigArgs` and
  `build-installer.ps1` has no `-Version`.
- `scripts/build-installer.ps1` reads the same file and refuses to build when
  the release executable reports a different version. An installer named after
  a development version, such as `ghostty-1.3.2-windows-x64-setup.exe`,
  therefore cannot be produced by accident.
- Both scripts fail if the file is missing, is not a valid Semantic Version, or
  its numeric part does not match `build.zig.zon`.
- A plain `zig build` does not read the file. It stays the development version
  `X.Y.Z-windows-+<hash>` with 0 as the fourth element, so development builds
  remain distinguishable from previews.
- `zig build -Dversion-string=...` itself is upstream's option and remains. When
  calling it directly from PowerShell, quote the argument
  (`'-Dversion-string=1.3.2-windows.4'`). Without quotes, PowerShell splits the
  value and the build fails with `error: InvalidVersion`.
- [ ] Confirm that the Windows changes and known limitations match
  `docs/windows.md` and `docs/windows-roadmap.md`.

In a normal build, the Git branch name and short commit hash are appended to
the major, minor, and patch from `build.zig.zon`. For example, a development
build on the `windows` branch has the form `X.Y.Z-windows-+abcdef0`.

## 4. Conditional Updates

### When Also Updating libghostty-vt

- [ ] Update `lib_version` in `build.zig`.
- [ ] Run the `-Demit-lib-vt` build and the relevant tests.
- [ ] For a Ghostty-core-only update, confirm that `lib_version` was not
  changed.

### When Updating the Bundled ConPTY Host

Ghostty ships `conpty.dll` and `OpenConsole.exe` next to its executable and
loads them in preference to the ConPTY in `kernel32.dll`, which drops the
escape sequences that carry images. They are pinned to one version of the
`Microsoft.Windows.Console.ConPTY` package and are fetched rather than
committed. See `vendor/conpty/README.md`.

This version moves independently of Ghostty's own, so it is not touched
during a normal version update.

- [ ] Update `$Version` and all three hashes in `scripts/fetch-conpty.ps1`:
  the package and both extracted files. Get them with `Get-FileHash`.
- [ ] Update the pinned version recorded in `vendor/conpty/README.md`.
- [ ] Re-run `./scripts/fetch-conpty.ps1 -Force` and confirm it reports the
  new version without a hash mismatch.
- [ ] Confirm both files are updated together. `conpty.dll` on its own
  silently falls back to the in-box host, so a mismatched pair looks like no
  change rather than an error.
- [ ] Start the build and confirm the log line
  `info(conpty): using the sideloaded conpty.dll next to our executable`,
  then confirm a program that draws with the Kitty graphics protocol still
  shows its image.

### When Creating a Source Tarball

- [ ] Confirm that package creation was explicitly requested.
- [ ] Check `VERSION` inside the tarball generated by `zig build dist`.
- [ ] Do not copy or commit `VERSION` into the working tree.

### When Creating an Installer

- [ ] Confirm that package creation was explicitly requested.
- [ ] Run `scripts/build-installer.ps1`. It takes the version from
  `dist/windows/version.txt`. Confirm that the installer's
  `ProductVersion` and numeric version match the executable (the script checks
  this).
- [ ] When signing, set the certificate subject name in the environment
  variable `CODESIGN_CERT`, add `-Sign`, and confirm that the resulting
  `ExecutableSignature` and `InstallerSignature` are `Valid`.
- [ ] Confirm that the output file name is
  `ghostty-X.Y.Z-windows.N-x64-setup.exe`.
- [ ] Confirm that the release tree has `bin\conpty.dll` and
  `bin\OpenConsole.exe` (the script refuses to build without them) and that
  the installed tree contains both plus `THIRD-PARTY-NOTICES.md`.

### When Tagging or Publishing

- [ ] Confirm that each commit, tag, push, and publish operation was explicitly
  requested.
- [ ] Name the tag `vX.Y.Z` for an upstream-equivalent version and
  `vX.Y.Z-windows.N` for a Windows preview, matching
  `dist/windows/version.txt`.
- [ ] The release build does not depend on where the tag points, so commits
  made after tagging, such as filling in verification results, do not change
  the version of the build.
- [ ] Confirm that the version passed to `.github/workflows/release-tag.yml`
  matches the tag.
- [ ] Before publishing, separately verify the signature, distribution format,
  and target architecture.

## 5. Verifying the Windows Build

A Release build can be verified with the following commands without creating
an archive or installer. The version comes from `dist/windows/version.txt`.

```powershell
./scripts/build-release.ps1

./zig-out/release/bin/ghostty.exe --version
./zig-out/release/bin/ghostty.exe +list-keybinds --default
```

- [ ] The Release build succeeds.
- [ ] `ghostty.exe --version` shows the intended `X.Y.Z-windows.N` (`X.Y.Z` for
  an upstream-equivalent version).
- [ ] `+list-keybinds --default` completes with exit code 0.
- [ ] The Release script reports the PE format, CPU, GUI subsystem, and
  required resources as valid.
- [ ] Launch the Release executable and verify terminal display and basic input
  on real hardware.
- [ ] Check the signature status with `Get-AuthenticodeSignature`.
- [ ] `git diff --check` succeeds.

## 6. Checking the Windows File Properties

`src/build/WindowsVersionResource.zig` generates a header from Ghostty's build
version, and `dist/windows/ghostty.rc` embeds it into the Windows version
information.

- The numeric version is stored in Windows' four elements as
  `major.minor.patch.N`. `N` is the value of the last pre-release identifier
  when it consists only of digits (4 for `1.3.2-windows.4`), and 0 otherwise
  (`-dev`, `-windows-` in normal builds, or no pre-release). Because the
  installer and winget use the numeric version to decide on updates, the
  numeric version changes with each preview.
- `FileVersion` and `ProductVersion` hold the full Semantic Version including
  pre-release and build metadata.
- Debug builds set `VS_FF_DEBUG`; Release builds clear it.
- The build fails if any of major, minor, patch, or the fourth-element sequence
  number exceeds the 16-bit limit (65535).

After updating the version, check the values through the Windows API as well,
separately from the CLI output.

```powershell
$info = (Get-Item -LiteralPath `
    './zig-out/release/bin/ghostty.exe').VersionInfo
$info.FileVersion
$info.ProductVersion
$info.FileMajorPart, $info.FileMinorPart, $info.FileBuildPart, $info.FilePrivatePart
```

- [ ] `FileVersion` and `ProductVersion` are not empty.
- [ ] The major, minor, and patch of both match `ghostty.exe --version`.
- [ ] `IsDebug` is `False` for the Release build.
- [ ] The fourth element of the numeric version (`FilePrivatePart`) is the
  sequence number `N` for a Windows preview and `0` otherwise.

## 7. After Updating

- [ ] List the changed files and confirm that only the intended scope is
  affected.
- [ ] Record the version, commit hash, build method, and signature status in
  the verification log.
- [ ] Reflect known limitations in the user-facing documentation.
- [ ] Commit and push only when explicitly requested.
